CORE CAPABILITIES

不是一组孤立功能，而是一条完整的发行经营链。

参考成熟 B2B 发行平台的设计方式，我们把企业真正每天会使用的能力，按“客户—内容—发行—数据—收益”重新组织。

品牌

品牌入口与独立域名

使用企业自己的品牌名称、Logo、服务入口和独立域名，让下游客户始终处于企业自己的业务界面。

客户

客户、厂牌与多账号

管理下游 CP、厂牌、音乐人及企业内部协作账号，让发行从“单账号工具”变成真正的 B2B 服务。

Catalog

内容与元数据中心

统一维护艺人、厂牌、专辑、歌曲、音频、封面、ISRC / UPC 及发行资料，减少信息散落在表格和聊天记录里。

发行

标准化发行工作台

从创建发行、选择渠道、设置时间，到提交、修改和下架，把重复的发行操作沉淀为清晰流程。

审核

两层审核与质量控制

企业先完成客户和内容检查，再进入看见音乐现有发行审核，尽量在送达 DSP 前发现资料和规范问题。

交付

全球渠道交付与状态

沿用现有 DSP 网络完成交付，并持续跟踪处理中、已交付、上线、失败等关键状态和异常。

维护

发行后的修改与下架

发行不是一次性动作。后续资料更新、重新交付、渠道维护与下架继续在同一业务链路里处理。

数据

平台数据与经营报表

集中查看发行结果和后续平台数据，让企业既能服务客户，也能理解自己的曲库和发行业务运行情况。

收益

收益、分账与提现

把平台收益报表、分账结果、待结算、可提现和提现记录接到发行之后，形成完整商业闭环。

DISTRIBUTION OPERATIONS

从一首歌进入系统，到发行后的持续经营。

企业级发行最重要的不是“能不能发”，而是每个月几百、几千甚至更多内容进入系统后，团队仍然能按同一套规则处理。

01

内容进入

客户或企业团队建立艺人、专辑、歌曲和必要发行资料。

02

企业审核

03

发行审核

04

DSP 交付

发送至目标平台并持续跟踪交付、失败、上线等状态。

05

持续经营

后续修改、下架、数据、收益、分账和提现继续留在同一业务链路。

OPERATE AT SCALE

业务规模扩大以后，不需要靠人工堆流程。

成熟 B2B 发行基础设施的核心价值之一，就是把大规模 Catalog 和重复发行操作从人工表格变成标准流程。企业版也围绕同一个目标组织能力。

01

批量内容进入

通过 Excel、SFTP、XML、DDEX 或 API 处理不同成熟度的批量数据和内容输入。

02

历史曲库迁移

针对已有大量历史 Catalog 的客户，确认字段映射、文件关系和迁移方式后逐步切换。

03

多客户统一运营

企业在一套后台管理多个下游客户，不必为不同厂牌维护完全独立的人工流程。

04

发行异常集中处理

把渠道交付失败、资料问题和后续状态集中到发行记录中，减少到处追问和重复确认。

05

统一数据与收益视图

发行完成后继续承接报表、收益和结算，避免“发行系统”和“经营系统”完全割裂。

06

按成熟度逐步集成

可以先用在线平台，也可以随着业务成熟逐步增加 API、DDEX、XML 或 SFTP，不要求一次性重做现有系统。

COMMON PROBLEMS

四类客户不同，但通常都在解决这三个问题。

不想再从零建设发行基础设施

发行背后不只有表单，还包含 Catalog、审核、渠道、状态、数据和收益。企业版让客户从现有底座开始，而不是重复造一遍。

业务规模扩大后，人工流程开始失控

客户、内容和发行量持续增长时，Excel、群聊和人工同步很难长期支撑，需要把流程、状态和责任沉淀进系统。

已有系统很多，不希望被迫全部替换

在线平台、API、DDEX、XML、SFTP、Excel 可以按现有成熟度组合，尽量减少一次性重构成本。

HOW TO CHOOSE

品牌平台、API，还是混合接入？看四个判断。

客户入口

是否需要自己的客户门户？

需要下游客户直接使用 → 优先品牌发行平台；纯内部能力 → API 可以更轻。

现有产品

是否已有成熟前端和账号体系？

已有完整产品 → API 优先；还没有完整发行产品 → 品牌平台更快。

数据规模

是否有大规模历史 Catalog？

有大量既有内容 → 需要优先设计迁移、批量导入和字段映射，而不是先改前端。

技术成熟度

FAQ

关于定价的常见问题。

年度平台费和发行使用费是什么关系？

年度平台费对应企业平台及版本能力；发行使用费按照实际“歌曲 × 目标渠道”产生的发行使用量计算。

基础版和专业版可以额外购买 API 吗？

可以。基础版与专业版可根据项目需要增购 API；企业版标准方案已包含 API 能力。

超过曲库规模怎么办？

可以升级版本或按扩容范围确认新的商业方案，大规模历史曲库迁移也可单独评估。

企业版为什么写“起”？

大型曲库、复杂迁移、DDEX、定制数据流和专属服务会根据项目实施范围确认最终报价。

发行流程

典型接入流程是先建立内容，再校验资料、提交发行并持续读取渠道状态。

// 接口结构示意，非正式生产 API
1. Create / sync artist, album and track
2. Validate release metadata
3. Configure target DSPs and schedule
4. Submit distribution
5. Receive status by query or webhook
6. Read reports / revenue after release

为什么先校验再提交？

发行链路包含大量渠道规则和必要元数据。把校验作为明确步骤，可以减少提交后才发现资料问题的返工成本。

Webhook

对于发行状态、交付结果等异步事件，Webhook 比持续轮询更适合企业级系统。

// 事件结构示意
{
  "event": "distribution.status.updated",
  "resource_id": "release_xxx",
  "status": "delivered",
  "channel": "example_dsp",
  "occurred_at": "..."
}

正式事件名称和字段以生产文档为准。
